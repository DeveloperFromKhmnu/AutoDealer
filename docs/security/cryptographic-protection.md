**Проєкт:** AutoDealerCRM

**Дата:** 2026-11-02

## 1. Симетричний криптографічний захист (ЛР №6)

### 1.1. Чутливі дані, що підлягають шифруванню
1. **VIN-код автомобіля (`CarLot.VinCodeEncrypted`):** 17-значний номер кузова є комерційною таємницею до моменту підписання договору, захищає від перехоплення лоту конкурентами на аукціоні.
2. **Аукціонна собівартість (`CarLot.AuctionCostEncrypted`):** Фінансова інформація про фактичну ціну викупу на аукціоні США (захист комерційної маржі).
3. **Номер телефону покупця (`BuyerRequest.PhoneEncrypted`):** Персональні дані клієнтів (вимога захисту персональних даних).

### 1.2. Вибір алгоритму та режиму: Чому не AES-CTR, а AES-256-GCM?
У ході лабораторного дослідження було виявлено критичну слабкість режиму AES-CTR: він є потоковим режимом без контролю цілісності (malleable). Маючи відому пару «відкритий текст — шифротекст», зловмисник може отримати гаму (`Keystream = C1 ^ P1`) та сформувати валідний модифікований шифротекст (`C2 = Gamma ^ P2`) без знання ключа шифрування.

Для усунення цієї вразливості в системі AutoDealerCRM реалізовано **автентифіковане симетричне шифрування AES-256-GCM** (Galois/Counter Mode, RFC 5116):
- **Розмір ключа:** 256 бітів (32 байти).
- **Вектор ініціалізації (Nonce):** 96 бітів (12 байтів), генерується криптографічно стійким генератором `RandomNumberGenerator` унікально для кожної операції шифрування.
- **Автентифікаційна мітка (Tag):** 128 бітів (16 байтів).

### 1.3. Формат збереження даних
Шифрування виконується сервісом `EncryptionService` перед записом у базу даних. Формат серіалізованого Base64-рядка:
```
[ Nonce (12 байтів) | Ciphertext (N байтів) | Auth Tag (16 байтів) ]
```

## 2. Контроль цілісності та автентичності (ЛР №7)

### 2.1. Захист полів бази даних (AES-256-GCM Tag)
- **Момент перевірки:** Під час кожного читання та розшифрування полів у `EncryptionService.Decrypt()`.
- **Реакція на модифікацію:** Якщо бодай один байт шифротексту або тегу змінено стороннім втручанням (наприклад, через SSMS чи SQL-ін'єкцію), клас `AesGcm` негайно генерує `CryptographicException`. Система перехоплює помилку, не розкриваючи пошкоджених даних, та позначає запис як «ПОМИЛКА ЦІЛІСНОСТІ».

### 2.2. Контроль автентичності ліцензійного файлу (`dealer.lic`)
- **Механізм:** Код автентичності повідомлення **HMAC-SHA256**.
- **Структура ліцензії:**
```json
{
  "Owner": "Cherniajev Auto Import LLC (КБЗІ-23-2)",
  "ExpiresAt": "2028-12-31T23:59:59Z",
  "Signature": "Base64(HMAC-SHA256(Owner + '|' + ExpiresAt, LicenseKey))"
}
```
- **Чому не звичайний хеш (SHA-256):** Хеш можна обчислити повторно після зміни даних. HMAC вимагає знання секретного ключа `License:Key`, що зберігається на захищеному сервері.
- **Захист від атак за часом (Timing Attacks):** Перевірка підпису виконується методом `CryptographicOperations.FixedTimeEquals()`.
- **Реакція на помилку:** У разі невірного підпису або закінчення терміну дії система автоматично переходить у статус **«Demo Mode»**, а спроба несанкціонованого завантаження записується в `Security Audit Log`.

## 3. Керування ключами та політика безпеки
1. **Зберігання ключів:** Ключ шифрування (`Encryption:Key`) та ліцензійний ключ (`License:Key`) винесені до файлу конфігурації `appsettings.Development.json` (який додано до `.gitignore`) або змінних оточення.
2. **Розділення ключів:** Для шифрування даних та підпису ліцензій використовуються різні незалежні 256-бітні ключі.
3. **Ротація:** Заміна ключів передбачає процедуру перешифрування існуючих записів БД новим ключем у фоновій міграції.
