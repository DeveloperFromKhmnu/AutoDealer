# Специфікація вимог — AutoDealerCRM

**Версія:** 1.0  
**Дата:** 2026-11-02  
**Статус:** Актуальна  
**Стандарти:** ISO/IEC/IEEE 29148:2018

---

## 1. Функціональні вимоги

### 1.1. Публічний каталог (Роль: Гість)

| ID | Вимога |
|----|--------|
| FR-01 | Система повинна відображати список автомобілів із такими полями: Марка, Модель, Рік випуску, Пробіг (км), Публічна ціна продажу (USD), Статус доставки. |
| FR-02 | Система повинна маскувати VIN-код у публічному каталозі: відображати перші 11 символів, а решту замінювати символами «*» (наприклад: `1HGCR2F83HA******`). |
| FR-03 | Система повинна підтримувати такі статуси доставки: «На аукціоні», «В дорозі», «На митниці», «В наявності». |
| FR-04 | Система повинна дозволяти гостям надсилати заявку на підбір авто з полями: ПІБ, номер телефону, побажання щодо моделі. |
| FR-05 | Після успішного надсилання заявки система повинна відображати повідомлення про підтвердження без перенаправлення на сторінку авторизації. |

### 1.2. Модуль менеджера (Роль: Менеджер)

| ID | Вимога |
|----|--------|
| FR-06 | Система повинна дозволяти менеджеру додавати новий лот автомобіля з полями: Марка, Модель, Рік, Пробіг, VIN-код (повний, 17 символів), Публічна ціна, Собівартість, Статус доставки. |
| FR-07 | Система повинна дозволяти менеджеру редагувати будь-яке поле наявного лоту. |
| FR-08 | Система повинна відображати менеджеру повний VIN-код (у розшифрованому вигляді) на сторінці деталей лоту. |
| FR-09 | Система повинна відображати менеджеру собівартість лоту (у розшифрованому вигляді). |
| FR-10 | Система повинна відображати менеджеру список заявок від покупців із розшифрованими телефонами та ПІБ. |
| FR-11 | Доступ до сторінок менеджера повинен бути заблокований для неавторизованих користувачів з перенаправленням на сторінку входу. |

### 1.3. Модуль адміністратора (Роль: Адміністратор)

| ID | Вимога |
|----|--------|
| FR-12 | Система повинна дозволяти адміністратору створювати облікові записи менеджерів із зазначенням логіну та початкового пароля. |
| FR-13 | Система повинна дозволяти адміністратору блокувати та розблоковувати облікові записи менеджерів. Заблокований менеджер не повинен мати можливості увійти до системи. |
| FR-14 | Система повинна надавати адміністратору сторінку керування ліцензією з відображенням статусу: «Demo» або «Licensed», дати закінчення дії, імені власника. |
| FR-15 | Система повинна дозволяти адміністратору завантажити файл ліцензії `dealer.lic` і перевірити його криптографічний підпис. |
| FR-16 | Система повинна вести журнал безпеки (Security Audit Log) з такими подіями: успішний вхід, невдалий вхід (логін та IP), вихід із системи, блокування/розблокування акаунту, завантаження ліцензійного файлу. |
| FR-17 | Адміністратор повинен мати доступ до перегляду журналу безпеки з фільтрацією за типом події та датою. |

### 1.4. Автентифікація та авторизація

| ID | Вимога |
|----|--------|
| FR-18 | Система повинна підтримувати вхід за логіном і паролем з видачею захищеної cookie-сесії. |
| FR-19 | Система повинна завершувати сесію користувача при виконанні дії «Вийти». |
| FR-20 | Паролі користувачів повинні зберігатися у базі даних виключно у вигляді хешу (BCrypt або PBKDF2). Зберігання паролів у відкритому вигляді заборонено. |
| FR-21 | Система повинна розмежовувати доступ до сторінок відповідно до ролі: сторінки менеджера недоступні гостям; сторінки адміністратора недоступні менеджерам. |

## 2. Нефункціональні вимоги

### 2.1. Безпека

| ID | Вимога |
|----|--------|
| NFR-01 | Поля VIN-код, номер телефону покупця та собівартість лоту повинні зберігатися в базі даних у зашифрованому вигляді (AES-256-CBC або AES-256-GCM). Розшифрування виконується виключно на рівні застосунку. |
| NFR-02 | Ключ шифрування не повинен зберігатися у вихідному коді або у репозиторії. Він повинен зчитуватися з конфігурації середовища (`appsettings.Development.json` або змінна середовища). |
| NFR-03 | Файл ліцензії `dealer.lic` повинен містити криптографічний підпис (HMAC-SHA256 або RSA-2048), що перевіряється при кожному завантаженні. Файл із недійсним підписом повинен відхилятися. |
| NFR-04 | Усі форми, що змінюють стан системи (додавання лоту, зміна акаунту, завантаження ліцензії), повинні бути захищені від CSRF-атак засобами ASP.NET Core AntiForgery. |
| NFR-05 | HTTP-відповіді повинні містити заголовки безпеки: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `X-XSS-Protection: 1; mode=block`. |

### 2.2. Надійність

| ID | Вимога |
|----|--------|
| NFR-06 | Застосунок повинен коректно обробляти виняткові ситуації (відсутність DB-з'єднання, помилки розшифрування) та повертати зрозумілу сторінку помилки без розкриття внутрішніх деталей стеку. |
| NFR-07 | Журнал безпеки (Audit Log) повинен зберігатися у базі даних і не залежати від доступності файлової системи. |

### 2.3. Сумісність і середовище

| ID | Вимога |
|----|--------|
| NFR-08 | Система повинна запускатися на .NET 8 Runtime під Windows 10/11 без необхідності інсталяції додаткових компонентів, окрім SQL Server LocalDB та .NET 8 SDK. |
| NFR-09 | База даних повинна створюватися автоматично під час першого запуску застосунку засобами EF Core Migrations (`Database.EnsureCreated` або `Migrate()`). |
| NFR-10 | Система повинна коректно відображатися у браузерах Chromium-сімейства (Chrome, Edge) у версіях, що підтримують ES2020. |

### 2.4. Зручність та обслуговуваність

| ID | Вимога |
|----|--------|
| NFR-11 | Вихідний код повинен відповідати стандартам C# coding conventions (Microsoft). Кожен контролер, сервіс і модель повинні бути в окремому файлі. |
| NFR-12 | Конфігурація підключення до бази даних та ключ шифрування не повинні бути закодовані жорстко (no hardcode) у вихідному коді. |
